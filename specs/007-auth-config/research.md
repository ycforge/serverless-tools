# Research: auth-config — `auth.yaml` формат и валидация scheme references (Project B)

**Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Все «Точки неоднозначности» spec.md уже закрыты информированными дефолтами (см. таблицу в spec, 2026-09-05); ниже — проектные решения уровня plan, вытекающие из них. Формат каждого решения: Decision / Rationale / Alternatives considered.

## R1 — YAML-парсер с детекцией дубликатов ключей (FR-007)

- **Decision**: `yaml` v2 (eemeli/yaml) как **devDependency**, вшитый в `dist` через tsup (`noExternal: ['yaml']`); published manifest `dependencies` остаётся пустым — у потребителя `@ycforge/composer` не появляется runtime-зависимостей, конвенция 006 «zero runtime dependencies» сохраняется. Парсинг идёт через `yaml.parseDocument()` с `uniqueKeys: true` (значение по умолчанию): любой `doc.errors` (включая `DUPLICATE_KEY`) — fail-fast ошибка. Дубликат ключа внутри маппинга `schemes` репортуется отдельным кодом `AUTH_DUPLICATE_SCHEME` с именем схемы (локализуется обходом AST `doc.contents`), дубликат любого другого ключа — `AUTH_DUPLICATE_KEY` с node-путём (например `schemes.user`). Детекция дубликатов покрывает весь документ — это строже минимального требования FR-007 (только `schemes`) и согласовано с Constitution V: файл с повторённым `version` неоднозначен и должен падать, а не «последний победил».
- **Rationale**: FR-007 требует fail-fast на дубликатах имён схем, а словари большинства парсеров молча оставляют последний ключ. `yaml` v2 — спецификационно-полный парсер, который видит дубликаты на уровне AST бесплатно; Node 22 не имеет встроенного YAML (`node:yaml` отсутствует), поэтому нужен внешний парсер. Bundling в dist через tsup сохраняет опубликованный манифест без runtime-зависимостей: tsup по умолчанию бандлит devDependencies, `noExternal` делает намерение явным и страхующим даже при случайном переносе `yaml` в `dependencies`.
- **Alternatives considered**: (a) **самописный subset-парсер** — отвергнут: YAML, даже в ограниченной схеме `auth.yaml`, — трактуемо большой формат (цитирование, block scalars, комментарии, flow-коллекции); риск тихого неверного разбора противоречит fail-fast (V), а объём и отладка несоразмерны; (b) **`js-yaml` + отдельный сканер дубликатов** — отвергнут: js-yaml сам дубликаты не видит (последний побеждает), параллельный лексический скан имеет собственные слепые зоны (quoted keys, flow mappings) и раздваивает кодовые пути; (c) **`yaml` как обычная runtime-зависимость** — отвергнут: ломает заявленную в 006 конвенцию пакета и заставляет потребителей тянуть `yaml` в своё dependency tree при том, что bundling решает тему без этого.

## R2 — Откуда читается `auth.yaml` (FR-001)

- **Decision**: `<appRoot>/auth.yaml`, где `appRoot` — корень openapi-приложения (composition) — **тот же самый `appRoot`, который 006 уже получает через `extractOpenApi({ appRoot })`**. Разрешение — `resolve(appRoot)`; файл отсутствует или не читается → `AUTH_FILE_MISSING` с resolved-путём. Признак «не YAML»/не-документ (список вместо map и т.п.) — `AUTH_FILE_INVALID_YAML` с тем же путём.
- **Rationale**: Assumptions spec (IDEA §8/§9/§13: `openapi/auth.yaml` рядом с `build_config.yaml`/`overrides.yaml`; «каждое со своим из них — composition»). Повторное использование `appRoot` из 006 не вводит второе понятие пути и даёт 008 единый composition input: `{ appRoot, authYaml, openApi }`.
- **Alternatives considered**: (a) **project-root** — отвергнут резолюцией «Точки неоднозначности» №1; (b) **явный `authPath` в запросе** — отвергнуто по YAGNI: один `auth.yaml` на composition, переопределение путей не требуется для 007 и аддитивно добавится контрактным обновлением, если появится.

## R3 — Поверхность валидации `function`-ссылок (FR-012)

- **Decision**: ссылка обязана иметь грамматику `functions.<name>`, где `<name>` — сегмент `[a-z][a-z0-9_]*` (грамматика сегмента заимствована из `parseResourceReference` в `@ycforge/pilot/contracts` — единый для репозитория стиль логических имён). Разрешимость — имя обязано присутствовать в caller-provided наборе `functions` (функции, доступные композиции); содержимое целевой функции не интроспектируется (FR-012 «SHALL NOT»). Нарушение грамматики → `AUTH_FUNCTION_INVALID_REF` с текстом ссылки; неразрешимое имя → `AUTH_FUNCTION_UNRESOLVED` с текстом ссылки.
- **Rationale**: spec Assumptions прямо говорят, что 009/011 (полная IDL/IDR-модель identity) не формализованы, и фиксируют минимальный поверхность: синтаксис §12 `functions.<name>` + разрешимость в набор функций composition input. Формат `functions.<name>` — двухсегментная логическая ссылка, а НЕ pilot `ResourceReference` `domain.name.property` (три сегмента, Terraform-ориентирован); смешивать их нельзя. Прозрачный источник набора (`functions` в запросе) не заставляет B читать `apps.yaml` или user-код — это зоны C и A (Constitution I).
- **Alternatives considered**: (a) **полный pilot `ResourceReference`** — отвергнут: §12 фиксирует `functions.<name>`, а трёхсегментный ref описывает ресурсы Terraform, не функции-authorizer'ы; (b) **B сам читает функции из `apps.yaml`** — отвергнут: поле `apps` принадлежит C, чтение user-файлов вне извлечённого OpenAPI нарушает FR-013 и границу I; (c) **валидация только синтаксиса без разрешимости** — отвергнута: без resolvability проверка «ссылка куда-то указывает» не имеет ценности (US3/AC2 требует отклонения несуществующей функции).

## R4 — Расширяемость модели scheme types (FR-005)

- **Decision**: типизированная discriminated union `AuthScheme` по литеральному полю `type` (`'none' | 'jwt' | 'function'`) + реестр валидаторов «тип → набор обязательных полей». Неизвестный `type` фатально падает на этапе до валидации полей: `AUTH_UNKNOWN_SCHEME_TYPE` с именем схемы и значением `type`; «no security» из неизвестного типа не выводится никогда. Добавление нового типа = новый член union + новая запись реестра + новый case в exhaustive switch; существующие `none`/`jwt`/`function`-валидаторы не модифицируются (SC-005, §12 «модель должна быть extensible»).
- **Rationale**: exhaustive переключение по литеральному типу не может молча свести неизвестное к «нет авторизации» — требуется явный case, которого нет → ошибка (Constitution V, «неизвестный тип никогда не игнорируется»). Реестр держит маппинг «тип → поля» декларативным и независимо тестируемым; расширение аддитивно по построению.
- **Alternatives considered**: (a) **открытый `type: string` с fallthrough** — отвергнут: риск тихой интерпретации неизвестного типа как no-security; (b) **один мономорфный валидатор с `if/else` по типу** — отвергнут: каждый новый тип правит общий код, расширение перестаёт быть аддитивным и хрупкое для регрессий (SC-005).

## R5 — Граница с spec 008 (defaultScheme-применение, securitySchemes-эмиссия)

- **Decision**: публичный результат 007 — валидированная read-model `AuthValidationResult { authYaml: AuthYamlDocument }`. 007 НИКОГДА не мутирует переданный `OpenApiDocument`, не применяет `defaultScheme` к операциям без `security`, не генерирует `components.securitySchemes` и API Gateway authorizers. Всё это — вход 008, который потребляет `{ appRoot, authYaml, openApi }`. Список NOT(007) зафиксирован в контракте отдельной секцией, чтобы имплементатор не «протёк» в 008 (Assumption «Граница к 008»).
- **Rationale**: spec Assumption; явный seam удерживает обзор и тесты в рамках 007 и делает результат проверяемым как «источник валиден + ссылки разрешимы», а не «документ частично скомпонован». Возврат только данных, а не побочных эффектов, упрощает и contract versioning (III — аддитивные изменения набора NOT не ломают потребителя).
- **Alternatives considered**: (a) **возвращать частично применённый документ (defaultScheme подставлен)** — отвергнут: утечка 008-поведения в 007, усложнение тестов и размытие границы I; (b) **валидатор молча пропускает naked-операции** — отвергнуто, но зафиксировано как ДОКУМЕНТИРОВАННОЕ поведение (US2/AC4: «на уровне 007 не ошибка»), а не магия: контракт и data-model явно перечисляют, что naked-операции не проверяются.

## R6 — Какие `security`-записи сканируются (FR-008/013)

- **Decision**: источник auth-требований — ИСКЛЮЧИТЕЛЬНО `security`-массив извлечённого OpenAPI: документный `security` (root) и `paths[*][method].security`. Сканируются ключи каждого security-requirement-объекта (`{ schemeName: scopes[] }`) как имена схем. Дескриптор маршрута в ошибке — `root` или `METHOD /path`. Отсутствие `security` на операции и `security: []` на уровне 007 не ошибки (применение defaultScheme — 008; пустой requirement — «явно без auth», не наше соблюдение). `components.securitySchemes` в извлечённом документе источником НЕ является и игнорируется: sources of truth для 008 — `auth.yaml` (генерирует свои securitySchemes), а собственные securitySchemes документа могут расходиться.
- **Rationale**: FR-013 («B читает только OpenAPI metadata») + US2; сканирование и root, и операций покрывает и документный дефолт, и per-operation override; маршрут в сообщении — требование US2/AC2. Игнорирование `components.securitySchemes` отделяет «что объявлено в composition» (auth.yaml) от «что NestJS положил в документ» — от последнего 007 не зависит (FR-009/013), и это явно документируется, а не умалчивается (V).
- **Alternatives considered**: (a) **валидировать и `components.securitySchemes` документа** — отвергнуто: 008 строит securitySchemes из `auth.yaml`, сверка с документными была бы дублем и ложным источником; (b) **только operation-level** — отвергнуто: root-`security` тоже несёт имена схем (US2/AC1 «все имена схем в security-записях»).

## R7 — Форма значения `audience` в `jwt`-схеме (FR-006)

- **Decision**: `audience` принимает либо scalar `string`, либо непустой массив строк; пустой массив трактуется как отсутствие поля → `AUTH_MISSING_FIELD`. `jwksUri` и `issuer` — непустые строки. Семантика значения не интерпретируется (это guard/шлюз-зона, FR-010/FR-011).
- **Rationale**: §12 показывает `audience: [my-api]` (список), но одиночная строка семантически эквивалентна и распространена; принятие обеих форм снимает ложные отклонения без расширения контракта интерпретацией. Ограничение «непустой» согласовано с общим принципом «непустые обязательные поля» в spec.
- **Alternatives considered**: (a) **только массив строк (строго по §12)** — отвергнуто: одиночный `audience: my-api` — валидное намерение автора, отклонять его значит вводить неоправданную строгость; (b) **принимать пустой массив** — отвергнуто: degenerate-значение, молчаливое принятие противоречит V.
