# Feature Specification: optional per-message error semantics for MQ batch

**Feature Branch**: `005-connector-mq-partial-failure`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User-provided feature id `005-connector-mq-partial-failure`; scope строки roadmap: «опциональная per-message семантика ошибок batch MQ» (`specs/README.md`). Зависимость: spec 001 (reverse-spec; фиксирует fail-fast batch-семантику как текущее поведение).

**Contribution**: когда одно сообщение в любом batch-доставке падает, текущая реализация отклоняет всю инвокацию (fail-fast), и Yandex Message Queue повторяет/отправляет в DLQ весь batch целиком; сообщения после упавшего не обрабатываются (docs/ARCHITECTURE.md §6.2 — «Batches run sequentially and fail fast», spec 004 FR-019). Spec 005 добавляет **опциональную** per-message семантику: приложение явно включает режим, в котором падение одного сообщения не останавливает обработку оставшихся, а исход (успех/провал) собирается по каждому сообщению. Без opt-in поведение остаётся байт-в-байт fail-fast (не ломает spec 001).

## Clarifications

### Session 2026-09-04

- **Q1 (итог инвокации при частичном провале)** → **вариант C, упрощён**: конфигурируемая политика **fail-fast** (дефолт, текущий spec 001) ИЛИ **degrade + DLQ** (новый режим). Fail-late убран как marginal: cloud повторяет весь batch целиком, poison-message продолжает блокировать, ценность над fail-fast + 004 logger минимальна. В режиме degrade приложение может указать `deadLetterQueueId` — ID очереди, в которую connector перепубликует упавшие сообщения (Yandex MQ не умеет это нативно); без `deadLetterQueueId` — потеря данных (выводится в лог как предупреждение). Degrade без `deadLetterQueueId` допустим только при явном согласии приложения.
- **Q2 (механизм opt-in)** → **variant B (ничего)**: per-handler opt-in архитектурно сломан (fan-out dispatch: каждое сообщение получает все `@QueueHandler`, семантика определяется на уровне batch-а). Механизм — transport-level опция в `QueueTransportOptions`; дефолт = fail-fast.
- **Q3 (границы failure сообщения)** → **вариант A**: только throw метода `@QueueHandler`; провал DI-разрешения провайдера и провал десериализации payload остаются whole-invocation failures (без продолжения).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Разработчик не блокирует очередь одним «отравленным» сообщением (Priority: P1)

Сервис обрабатывает batch Message Queue-доставки. Одно из сообщений стабильно падает (например, невалидный payload под один `@QueueHandler`). При текущей семантике это сообщение заставляет всю инвокацию падать, платформенный retry повторяет **весь** batch, «хорошие» сообщения стоят за «отравленным» сообщением и не обрабатываются, пока оно есть в очереди. Разработчик включает опциональную per-message семантику: обработка **продолжается** к следующим сообщениям после упавшего, каждое сообщение попытано, и решение о том, что делать с упавшим, выносится по собранному результату.

**Why this priority**: разблокировка очереди — базовый практический сценарий. Без продолжения обработки одна poison-message останавливает всю доставку (текущий MVP в 001/004 — только fail-fast). Это самый ценный и самодостаточный slice.

**Independent Test**: фикстура batch из сообщений, где `messages[1]` падает в handler-е: с opt-in-режимом `messages[0]` и `messages[2]` обрабатываются, `messages[1]` зафиксирован как failure; без opt-in весь batch отклоняется на первом сообщении (паритет 001).

**Acceptance Scenarios**:

1. **Given** приложение включило per-message семантику, **When** одно из сообщений batch-а падает в обработчике, **Then** обработка переходит к оставшимся сообщениям (каждое последующее попытано), а не останавливается на упавшем.
2. **Given** per-message семантика не включена (дефолт), **When** сообщение падает, **Then** инвокация отклоняется немедленно, последующие сообщения не пытаются (паритет spec 001 fail-fast, байт-в-байт).
3. **Given** batch, где ВСЕ сообщения успешны, **When** обработка завершается, **Then** результат детерминирован и не отличается от успешного fail-fast пути (никакого регресса успешного конверта).

---

### User Story 2 — Разработчик видит per-message исход для связки с трассировкой (Priority: P2)

Обработка batch-а в per-message режиме может иметь несколько упавших сообщений. Разработчику нужен доступ к per-message исходу — какой `messageId` упал/прошёл — и связка каждого исхода с `trace_id` текущей инвокации (за счёт observability из spec 004), чтобы соотнести слоган с конкретным сообщением без потери сквозной корреляции.

**Why this priority**: продолжение без observability — это слепой сброс; ценность partial-failure раскрывается через видимость упавших сообщений и их корреляцию с общим `trace_id`. Однако само продолжение (US1) уже самостоятельный MVP, поэтому US2 — второй приоритет.

**Independent Test**: интеграционный тест batch-а с двумя упавшими и одним успешным сообщением: результат содержит per-message исходы (messageId → success/failure), а связанный stdout-лог (спец 004) несёт общий `trace_id` и упоминание упавших сообщений без значений payload.

**Acceptance Scenarios**:

1. **Given** batch с несколькими упавшими сообщениями в per-message режиме, **When** обработка завершается, **Then** собранный результат содержит исход по каждому `messageId` (успех или класс ошибки), powering связку приложения.
2. **Given** инвокация в per-message режиме, **When** логируется (спец 004), **Then** per-message failure-записи несут общий `trace_id`/`awsRequestId` инвокации и НЕ содержат значений payload/токенов/`raw` (редакция §6.2).
3. **Given** per-message результат, **When** приложение обращается к нему, **Then** он не содержит значений payload/header (только `messageId`, индекс/класс ошибки) — безопасен для логирования.

---

### User Story 3 — Разработчик управляет финальным исходом batch-а при частичном провале (Priority: P2)

После того как в per-message режиме собраны исходы всех сообщений, приложение/платформа должна принимать решение о судьбе упавших сообщений. Yandex Message Queue подтверждает/повторяет доставку целиком (возврат успеха = ack всего batch-а; исключение = retry всего batch-а), поэтому «индивидуальный ack» на уровне платформы невозможен. Управляемым является **итог инвокации**: как connector формирует результат batch-а по собранному набору исходов.

**Why this priority**: без определённого исхода US1/US2 оставляют неоднозначным, «ackнуты» ли упавшие сообщения (потенциально теряются) или повторяются. Это контрактный выбор с разными последствиями для доставки; уточняется в Q1–Q3 ниже.

**Independent Test**: для каждой выбранной политики итога — интеграционный тест: batch с упавшим сообщением завершается предсказуемым итогом (успех/исключение) в соответствии с политикой, при сохранении per-message исходов из US2.

**Acceptance Scenarios**:

1. **Given** приложение включило degrade + DLQ, **When** есть упавшее сообщение, **Then** инвокация возвращает успех (ack), а упавшие сообщения перепубликованы в DLQ по `deadLetterQueueId` для out-of-band обработки.
2. **Given** приложение включило degrade без `deadLetterQueueId`, **When** есть упавшее сообщение, **Then** инвокация возвращает успех (ack), в логе пишется предупреждение о потере данных; упавшие сообщения не перепубликованы.
3. **Given** приложение НЕ включило degrade (дефолт fail-fast), **When** сообщение падает, **Then** инвокация отклоняется; платформа повторяет весь batch (паритет spec 001, байт-в-байт).

---

### Edge Cases

- Пустой batch (`messages: []` — не MQ-вызов → `UNKNOWN_INVOCATION_EVENT`): остаётся за границей транспорта, per-message режим не активируется.
- Провал DI-разрешения провайдера или десериализации payload: это НЕ per-message failure, а whole-invocation фейл (не продолжают batch; Q3 → A).
- Warm-инвокация N+1: per-message результат одного batch-а НЕ виден в следующем (изоляция invocation scope, spec 001 FR-009); состояние между инвокациями отсутствует.
- Провал разрешения провайдера или сбой, возникающий до входа в per-message-цикл (например, `noQueueHandler`, провал discovery/валидации события, init-ошибка): это НЕ per-message failure, а whole-invocation фейл как в 001 (не подлежит продолжению).
- **Транзакционность обработки одного сообщения**: в рамках обработки batch-а вся работа по одному сообщению должна быть атомарной. Если первое сообщение выполнило неповторяемые изменения, а второе упало — платформа перезапустит batch с 0, и первое выполнится заново (дублирование). Connector предоставляет per-message scope-изоляцию; ответственность за атомарность non-idempotent операций лежит на приложении (FR-012). Приложение должно быть идемпотентным или оборачивать side effects в транзакцию с outer idempotency-key.
- Переполнение/ошибка сбора результата не должна менять транспортный итог (fail-open, spec 004 FR-010/015); сбой observability не роняет обработку.
- Конкурентные инвокации: per-message исходы не должны пересекаться между вызовами (атомарность, spec 004 FR-011).
- Итог инвокации при частичном провале: degrade + DLQ (Q1 → C simplified); fail-late убран (малая ценность, cloud повторяет весь batch); transport-level opt-in (Q2 → B).

## Requirements *(mandatory)*

### Functional Requirements

Per-message processing:

- **FR-001**: THE CONNECTOR SHALL продлевать обработку batch-а к следующим сообщениям после failure сообщения **только** когда per-message семантика явно включена приложением; иначе — текущий fail-fast (spec 001, байт-в-байт). (US1/AC1–AC2; Q2.)
- **FR-002**: THE CONNECTOR SHALL собирать исход (успех/failure) по каждому сообщению batch-а в per-message режиме, сохраняя привязку к `messageId`. (US2/AC1.)
- **FR-003**: THE CONNECTOR SHALL сохранять детерминированный порядок попыток сообщений (порядок доставки) в per-message режиме; результат — в том же порядке, что и `batch.messages`. (US1/AC3, spec 001 FR-…: batch iteration order.)
- **FR-004**: THE CONNECTOR SHALL НЕ менять успешный исход и результаты обработки, когда все сообщения успешны — per-message успешный путь эквивалентен fail-fast успешному пути. (US1/AC3.)

Failure scope & outcome:

- **FR-005**: THE CONNECTOR SHALL трактовать как per-message failure только throw метода `@QueueHandler`; провал DI-разрешения провайдера и провал десериализации payload остаются whole-invocation failures (не продолжают batch). (US2/AC1; Q3 → A.)
- **FR-006**: THE CONNECTOR SHALL при наличии per-message failure в режиме degrade: подтвердить batch (invoкация возвращает успех), а упавшие сообщения перепубликовать в указанную `deadLetterQueueId`-очередь (Yandex MQ нативно это не поддерживает). При отсутствии `deadLetterQueueId` — упавшие сообщения теряются, но в лог пишется предупреждение; такой режим допустим только при явном согласии приложения. (US3; Q1 → C simplified.)
- **FR-007**: THE CONNECTOR SHALL обрабатывать как whole-invocation failure (НЕ per-message, без продолжения) сбои, возникающие до/вне per-message-цикла: `noQueueHandler`, провал discovery, провал валидации события, init/bootstrap-ошибки. (edge cases; parity 001.)
- **FR-008**: THE CONNECTOR SHALL включать per-message семантику ТОЛЬКО через transport-level опцию в `QueueTransportOptions` (один switch на весь runtime); per-handler опция отсутствует (fan-out dispatch: семантика определяется на уровне batch-а, а не обработчика). Дефолт — fail-fast (spec 001). (Constitution V — явное вместо магии; Q2 → B.)

Observability (integration with spec 004):

- **FR-009**: THE CONNECTOR SHALL связывать per-message failure-записи с `trace_id`/`awsRequestId` текущей инвокации, единым для всего batch-а, когда доступен observability-провайдер/логгер (спец 004). (US2/AC2.)
- **FR-010**: THE CONNECTOR SHALL НЕ раскрывать в per-message результате и в логе значений payload, токенов, headers/`raw` (редакция §6.2; spec 004 FR-009/014) — только `messageId`, класс/код ошибки. (US2/AC3, edge case fail-open.)

Guarantees & parity:

- **FR-011**: THE CONNECTOR SHALL быть fail-open: сбой сбора результата/наблюдаемости SHALL NOT изменять транспортный итог (спец 004 FR-010/015). (edge case.)
- **FR-012**: THE CONNECTOR SHALL изолировать per-message результат одной инвокации от других (spec 001 FR-009; никакого перекоса между конкурентными вызовами). (edge case, spec 004 FR-011.)
- **FR-013**: THE CONNECTOR SHALL NOT менять поведение HTTP-транспорта и wire-конверт успешных ответов (спец 001 FR-017; изменения только в MQ-пути). (parity.)

### Key Entities *(include if feature involves data)*

- **MessageOutcome**: per-message исход обработки — `messageId`, признак успеха, для failure — ограниченный тип (класс/код ошибки, без значений payload); агрегируется в собранный результат batch-а.
- **BatchDispatchResult**: собранный результат per-message режима — перечисление `MessageOutcome` в порядке `batch.messages`, из которого приложение/политика выводит итог инвокации.
- **PartialFailurePolicy**: итог инвокации при наличии per-message failure — fail-fast (дефолт) или degrade + DLQ (opt-in).
- **PartialFailureOptIn**: transport-level опция в `QueueTransportOptions` (один switch на весь runtime; per-handler отсутствует).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Каждый acceptance scenario US1–US3 покрыт минимум одним выполняемым тестом; выполнение `pnpm --filter @ycforge/nestjs-connector test` зелёное (traceability, Constitution II).
- **SC-002**: В per-message режиме batch из N сообщений с K упавшими попытает все N (каждое сообщение после каждого упавшего), и результат содержит исходы для N/N сообщений (иначе — fail-fast, N попытано до первого failure). (US1.)
- **SC-003**: Без opt-in (дефолт) поведение байт-в-байт совпадает со spec 001: первый failure останавливает инвокацию; результат/исключение не отличаются. (US1/AC2, parity.)
- **SC-004**: Per-message результат и лог не содержат значений payload/токенов/headers/`raw` в 100% случаев (автоматический тест редакции). (US2, FR-010.)
- **SC-005**: Итог инвокации при частичном провале детерминирован и соответствует выбранной политике в 100% случаев теста (US3, FR-006).
- **SC-006**: Успешный batch в per-message режиме даёт тот же результат, что и успешный fail-fast batch (паритет успешного пути, FR-004).

## Assumptions

- Зависимость формально — spec 001 (по roadmap). Spec 004 (observability, `trace_id`/логгер) считается доступной и используется для per-message failure-наблюдаемости (обычно это уменьшает объём изменений против дублирования логов); HTTP/wire-параметры при этом не меняются.
- Yandex Message Queue подтверждает/повторяет **всю** доставку целиком: индивидуальный ack по сообщению на уровне платформы невозможен (**observed**). Поэтому «per-message семантика» реализуется на уровне обработки и итога инвокации (Q1), а не на уровне платформенного ack-а.
- По умолчанию (без opt-in) поведение — текущий fail-fast из spec 001/004; spec 005 добавляет только аддитивный опциональный режим, чтобы не ломать существующий контракт и паритетные тесты.
- Механика retry/dead-letter остаётся за Yandex Message Queue (спец 001 FR-026, spec 004 FR-019) для fail-fast режима (дефолт); в режиме degrade connector выполняет перепубликацию упавших сообщений в указанную `deadLetterQueueId`-очередь; без `deadLetterQueueId` — потеря данных с предупреждением в логе (только при явном согласии приложения).
- **Транзакционность обработки одного сообщения**: Yandex MQ подтверждает/повторяет доставку целиком (возврат успеха = ack всего batch-а; исключение = retry всего batch-а). Если первое сообщение выполнило неповторяемые изменения и возвращён успех, а второе упало — success ack'нут; если второе упало и функция бросила — retry начнёт batch с 0, и первое выполнится заново. Connector предоставляет per-message scope-изоляцию; ответственность за атомарность non-idempotent операций лежит на приложении (транзакция + idempotency-key на уровне приложения).
- Per-message результат — для приложения/наблюдаемости; он не становится HTTP-конвертом и не мигрирует в другие транспорты (спец 001 FR-019/FR-026).
- Ограничение текущего триггера (группа = 1 сообщение, observed) сохраняется: batch-модель остаётся авторитетной, per-message режим работает на любом размере batch-а.
